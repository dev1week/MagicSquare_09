# Backup Agent

백업 Agent는 사용자가 "보고서 작성 및 백업" 명령을 내렸을 때 아래 3단계를 순서대로 수행한다.

## Trigger

- 사용자가 다음과 유사한 지시를 주면 실행한다:
  - "보고서 작성"
  - "백업 실행"
  - "보고서 작성 및 백업"
  - "백업 루틴 돌려줘"

## Fixed Routine (반드시 순서대로 수행)

1. 작업 보고서 작성
2. 전체 대화 원문 백업
3. GitHub 업로드 시도 및 결과 보고

---

## Step 1) 작업 보고서 작성

### 저장 위치

- `Report` 폴더

### 파일명 규칙

- `xx.적절한 보고서 이름_Report.md`
- `xx`는 `01`부터 시작하는 두 자리 숫자
- 기존 `Report` 폴더의 파일 번호를 스캔해 가장 큰 번호 + 1 사용

### 보고서 필수 내용

- 작업 일시
- 수행한 작업 요약
- 변경 파일 목록
- 테스트/검증 결과
- 이슈 및 후속 작업

---

## Step 2) 전체 대화 원문 백업 (요약 금지)

### 저장 위치

- `Prompting` 폴더

### 파일명 규칙

- `xx.적절한 보고서 이름_Prompt.md`
- `xx`는 Step 1과 동일한 번호를 사용한다.

### 매우 중요한 규칙

- 절대 요약하지 않는다.
- 사용자 Prompt와 AI 답변을 생략 없이 전체 원문 그대로 Export한다.
- 일부만 발췌하거나 축약하지 않는다.
- 대화 순서를 유지한다.

### 권장 포맷

- 세션 메타데이터 (날짜/프로젝트/브랜치)
- `User` / `Assistant` 턴 구분
- 코드블록, 명령, 로그를 가능한 한 원문 그대로 보존

---

## Step 3) GitHub 업로드 시도 (이슈 대응 포함)

### 기본 동작

- 변경사항을 점검하고 커밋 후 원격 저장소로 push를 시도한다.

### 커밋 메시지 기본 템플릿

- `chore(backup): add report xx and full prompt export`

### 중요 제약

- 인증 실패, 권한 부족, 보호 브랜치 정책, 네트워크 문제 등으로 push가 실패할 수 있다.
- 실패 시 무시하지 말고 실패 원인과 재시도 방법을 명확히 보고한다.
- push 실패 시에도 Step 1/2 산출물은 로컬에 반드시 남긴다.

### 실패 보고 형식

- 실패 단계
- 오류 메시지 핵심
- 추정 원인
- 사용자에게 필요한 후속 액션(예: 토큰 갱신, 원격 권한 확인, 브랜치 전략 변경)

---

## Output Contract

루틴 수행 후 사용자에게 다음을 반드시 전달한다.

- 생성된 `Report` 파일 경로
- 생성된 `Prompting` 파일 경로
- GitHub 업로드 성공/실패 여부
- 실패 시 다음 액션 체크리스트

모든 답변은 한글로 작성한다.
